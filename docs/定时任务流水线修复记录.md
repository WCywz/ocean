# 定时任务流水线修复记录

## 问题背景

系统设计了模拟时间机制：每天凌晨 00:05（真实时间）由 `SystemDateTask` 推进"系统日期"，然后各个任务按 cron 时间依次执行：

| 时间 | 任务 | 职责 |
|---|---|---|
| 00:05 | SystemDateTask | 系统日期 +1 天 |
| 01:00 | ObservationIngestTask | 观测数据入库（observation_data + observation_grid） |
| 02:00 | DataSyncTask | 模型预报（forecast_grid） |
| 02:30 | HealthAssessmentTask | 健康评估（health_record） |

### 问题 1：任务独立触发，不串联

四个任务各自靠 Spring `@Scheduled` cron 触发，互不依赖。`SystemDateTask` 推进日期后不触发后续任务。如果应用在 01:00/02:00/02:30 未运行（本地开发白天才启动），数据就永远不会入库。

### 问题 2：启动无补录机制

生产环境 nohup 24h 运行，cron 任务按时触发。但本地开发环境每天启动后没有任何检查补录机制，缺失的数据需要手动调 API 补跑。

---

## 修复方案

三层保障体系：

```
应用启动
  └─ StartupCatchUpTask  @Async 异步补录检查

每天 00:05
  └─ SystemDateTask      推进日期 → 观测 → 预报 → 健康（主链路）

01:00  ObservationIngestTask   已入库则跳过，无则加锁补录
02:00  DataSyncTask            已预报则跳过，无则加锁补录
02:30  HealthAssessmentTask    已评估则跳过，无则加锁补录
```

## 第一次修复（2026-05-25）

### 修改清单

#### 新增文件

**`PipelineLockService.java`**（`com.ocean.service`）

统一管理流水线串行化锁 + 数据状态查询：

- `tryLock()` / `unlock()` — `ReentrantLock` 保证同一时刻只有一个流水线在执行
- `isObservationIngested(LocalDate)` — 同时检查 `observation_data` 和 `observation_grid`
- `isForecastComplete(LocalDate)` — 检查 `forecast_grid`
- `isHealthAssessed(LocalDate)` — 检查 `health_record`

**`StartupCatchUpTask.java`**（`com.ocean.task`）

应用启动后异步检查当天数据流水线完整性，缺失步骤自动补录。标注 `@Async` 避免阻塞启动。

#### 修改文件

| 文件 | 改动 |
|---|---|
| `OceanApplication.java` | 新增 `@EnableAsync` |
| `SystemDateTask.java` | 推进日期后串联执行观测入库 → 预报 → 健康评估，每个步骤独立 try-catch；引入锁保护 |
| `ObservationIngestTask.java` | 改为先查 `PipelineLockService` 状态，已入库跳过；加锁执行 |
| `DataSyncTask.java` | 同上模式，先查后补 |
| `HealthAssessmentTask.java` | 同上模式，先查后补 |
| `ForecastServiceImpl.java` | prepare 子进程 120s 超时、推理子进程 300s 超时；临时文件清理失败时记录日志 |

### Code Review 发现与修复对照

| # | 严重 | 问题 | 修复方式 |
|---|------|------|----------|
| 1 | Critical | `StartupCatchUpTask`（ApplicationReadyEvent 线程）和 `SystemDateTask`（scheduler 线程）在 00:05 附近可能并发执行 | `ReentrantLock.tryLock()` 保证互斥 |
| 2 | Critical | 重复检查只看 `observation_data`，`observation_grid` 缺失不会被检测到 | `isObservationIngested` 同时查两张表 |
| 3 | Important | 所有重复检查都有 TOCTOU 竞态条件 | 锁内 check-then-act，其他线程 `tryLock` 失败直接跳过 |
| 4 | Important | `selectCount` + `last("LIMIT 1")` 重复 7 次 | 收拢到 `PipelineLockService` 三个查询方法 |
| 5 | Important | `runForecast()` 子进程无超时，模型挂了会永远阻塞 | prepare 120s / 推理 300s 超时 |
| 7 | Important | `StartupCatchUpTask` 同步执行阻塞 `ApplicationReadyEvent` 线程 | 加 `@Async` 异步执行 |
| 8 | Important | 部分数据写入 + 异常后，下次检查被 `count > 0` 骗过 | 双表都检查，部分写入时另一张为空会重跑 |
| 10 | Minor | 临时 CSV 删除失败静默吞异常 | 改为 `log.warn` |

### 待后续改进

- **#6**（Important）：`forecast_date` 检查可能与模型实际输出日期不匹配（多日预报场景）
- **#9**（Minor）：`HealthAssessmentTask` 同时承担 scheduler 和 service 两个角色，建议提取 `HealthAssessmentService`
- **#11**（Minor）：`last("LIMIT 1")` 是 MySQL 特有语法，已收到 `PipelineLockService` 便于后续统一修改
- **#8 完整方案**：`count > 0` 不如用 `pipeline_status` 表显式跟踪完成状态，避免部分写入导致的误判

## 第二轮 Code Review（2026-05-25）

### 发现的问题

| # | 严重 | 问题 | 根因 |
|---|------|------|------|
| C1 | Critical | `@Async` 使用默认 `SimpleAsyncTaskExecutor`，无界线程、不复用、静默吞异常 | `@EnableAsync` 未配置自定义线程池 |
| C2 | Critical | forecast 超时被 stdout 阻塞读取绕过——`readLine()` 在 `waitFor()` 之前，进程挂死则永远阻塞 | 读取输出和超时检查顺序错误 |
| I1 | Important | `advanceDay()` 在 `tryLock()` 之前，锁被占用时日期已推进但流水线未跑，55 分钟窗口期内前端看到空数据 | 日期推进和锁获取顺序颠倒 |
| I2 | Important | 所有兜底任务先查状态再获取锁（TOCTOU 模式） | 设计模式：check-then-lock |
| I3 | Important | `StartupCatchUpTask` 锁前读取的布尔值在锁内继续使用 | 与 I2 同类 |
| I4 | Important | `@Async` 方法无顶层异常捕获，未覆盖路径的异常静默丢失 | 与 C1 同类 |
| I5 | Important | 健康评估 upsert 非原子（select → delete → insert），崩溃导致记录丢失 | 无 `@Transactional` |
| I6 | Important | 预报入库非原子（delete → insert），崩溃导致 forecast_grid 当天数据全部丢失 | 无 `@Transactional` |
| M1 | Minor | 全部使用 `@Autowired` 字段注入而非构造器注入 | 代码风格 |
| M2 | Minor | `PipelineLockService.unlock()` 独立暴露，误用抛 `IllegalMonitorStateException` | API 设计 |
| M3 | Minor | 三个兜底任务有相同的 check-then-lock 样板代码 | 重复代码 |

### 修复计划

| # | 修复方式 |
|---|----------|
| C1 | 添加 `ThreadPoolTaskExecutor` bean，固定 2 核心/4 最大线程，有界队列 + CallerRunsPolicy |
| C2 | 将 stdout/stderr 消费放到独立线程，主线程 `waitFor(timeout)`，超时后取消消费线程 |
| I1 | `advanceDay()` 移到 `tryLock()` 成功之后 |
| I2, I3 | 所有任务改为 lock-then-check 模式：先获取锁，再检查数据状态，已在则释放 |
| I4 | `catchUp()` 方法体包裹顶层 try-catch，记录 ERROR 日志 |
| I5, I6 | 标注为已知风险（需要 `@Transactional` 或 upsert 改写），本轮暂不修 |
| M1-M3 | 标注为后续优化，本轮暂不修 |

### 第二轮修复变更

| 文件 | 改动 |
|---|---|
| `AsyncConfig.java`（新增） | 配置 `ThreadPoolTaskExecutor`：core=2, max=4, queue=10, CallerRunsPolicy |
| `ForecastServiceImpl.java` | prepare 和推理子进程的 stdout 消费移到独立线程，`waitFor(timeout)` → 超时 → `destroyForcibly` + `interrupt` |
| `SystemDateTask.java` | `advanceDay()` 移到 `tryLock()` 成功之后 |
| `ObservationIngestTask.java` | check-then-lock → lock-then-check |
| `DataSyncTask.java` | check-then-lock → lock-then-check |
| `HealthAssessmentTask.java` | check-then-lock → lock-then-check |
| `StartupCatchUpTask.java` | lock-then-check + 顶层 try-catch 防止 `@Async` 异常静默丢失 |

### 待后续改进（第二轮）

- **I5**（Important）：健康评估 upsert 非原子（select → delete → insert），建议加 `@Transactional` 或 `saveOrUpdate`
- **I6**（Important）：预报入库非原子（delete → insert），建议加 `@Transactional`
- **M1**（Minor）：`@Autowired` 字段注入 → 构造器注入
- **M2**（Minor）：`PipelineLockService.unlock()` 独立暴露有误用风险
- **M3**（Minor）：三个兜底任务 lock-then-check 样板代码可收拢到 `PipelineLockService.executeIfMissing()`

## 第三轮 Code Review（2026-05-25）

|---|---|---|---|
| N1 | Important | `Thread.join(5000)` 抛出 `InterruptedException` 被外层 `catch (Exception)` 吞掉，中断标志丢失 | Java 规范要求被中断后恢复中断状态或重新抛出 |

| N3 | Suggestion | prepare 脚本超时后 `return result`，调用方不感知超时日志详情（result 仅含简短 message） | 超时时的 `prepareLog` 内容未被保留到 result 中 |
